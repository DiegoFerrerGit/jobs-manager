# Roadmap — V2

V1 works end to end: n8n discovers companies, collects postings, filters them and writes to
PostgreSQL; the app reads and tracks them. This document lists what V1 deliberately left out,
why, and what it would take to build it.

Nothing here is required for the pipeline to keep running.

---

## 0. What has already shipped

Items that were on this list and are now done, so they are not planned twice:

- **Closed postings.** `jobs.closed_at` plus a `Mark closed` node at the end of workflow 3.
  A posting not seen for 7 days is marked closed, and reopens by itself if the company
  republishes it. Only the frontend side is pending: hide closed rows by default, and keep
  showing the ones already applied to with a grey badge.
- **Adding a company by pasting its job board URL**, from the settings modal. Ashby, Greenhouse,
  Lever, Teamtailor, Workday, Workable and Oracle are recognised; anything else is stored as
  `custom`.
- **Company–posting attribution by URL.** Postings used to be matched back to their company by
  item index, which silently broke whenever a Lever response was split into several items —
  roughly 90% of ATS postings were being dropped or attributed to the wrong company. The company
  is now resolved from the slug inside the posting's own URL.
- **Ashby secondary locations.** Ashby puts the main country in `location` and the rest in
  `secondaryLocations`. Only the first was being read, which hid every LATAM opening at
  companies whose primary listing is US or European.
- **Get on Board as a fourth source.** A LATAM-native job board with a free public API. See the
  note under coverage for what it is actually worth. (Note: Salaries are now automatically
  normalised to an annual rate and labeled "Annual" in the UI).
- **CV Editor (`/cv`).** Built-in Typst IDE to write, preview, and store ATS-friendly resumes.
  Code is persisted to PostgreSQL and rendered into PDF securely through a local compiler
  inside Next.js.
- **Priority Info UI.** Added an info modal in the jobs view explaining the priority tiers
  (High = manager, Medium = lead/staff, Low = ic) derived from job titles.

## 1. Wider coverage

### Google search (blocked on cost)

The aggregator indexes ~95k companies but not all of them — Span, for instance, is missing and
had to be added by hand. Google indexes every public job board, so a handful of queries like
`site:jobs.ashbyhq.com "Buenos Aires" engineer` would close that gap.

**What happened with Serper.** The workflow already has the nodes built (`Google queries` →
`Search Google (Serper)` → `Companies from Google`), currently disabled. Their free tier
rejects the requests:

```
400 — Query pattern not allowed for free accounts
```

The `site:` operator is paid-only. Their cheapest pack is **USD 50 for 50k credits, expiring in
6 months**, and queries asking for more than 10 results cost 2 credits instead of 1. At 16
queries per week (~400 per six months) that is under 1% utilisation — poor value.

**Options, cheapest first:**

| Option | Cost | Trade-off |
|---|---|---|
| Drop `site:` and filter by domain in the code | Free | Google still ranks the domain highly when named as plain text, but results are noisier and fewer |
| Pay-as-you-go SERP provider (Serpent API, DataForSEO) | ~USD 10 deposit, ~USD 0.60 / 1k queries, no expiry | Different vendor, response shape must be mapped in `Companies from Google` |
| Serper paid pack | USD 50 / 6 months | Nodes work as-is, no code changes |

**Recommendation:** try the free variant first. If it surfaces companies the aggregator misses,
it costs nothing. If it comes back thin, a pay-as-you-go provider is a few dollars a year.
Serper only makes sense if the search volume grows a lot.

### LinkedIn job alerts

LinkedIn emails saved-search alerts. A Gmail trigger in n8n could parse those emails, extract
company names, and feed them into the same discovery flow — free, and it surfaces companies
that post only on LinkedIn.

### Own-website companies (`custom`)

Companies added by URL that do not use a known ATS are stored with `ats = 'custom'` and never
queried. Litebox is the example: it publishes openings on its own site. Closing this needs a
scraper (Firecrawl or similar) that takes the careers URL and returns title, location and link.

This is also what would make Gusto job boards readable — InTune Analytics publishes there, and
Gusto has no public API.

### Get on Board: keep expectations low

The branch works and costs nothing, but after filtering it yields around fifteen postings, all
individual-contributor, mostly at consultancies and outsourcing firms, with local-market
salaries. The board's model is agencies hiring for clients, not product companies.

Worth leaving on because it is already built. Not worth investing in further. The real volume
keeps coming from Greenhouse and Ashby.

The consultancy exclusion list (`STAFFING`) currently lives hardcoded in `Filter GOB` and has to
be grown by hand. It belongs in the database — see the next section.

## 2. Blacklist and per-user rules

Excluding a company still means running SQL by hand, and it only works for ATS companies:
YC and Get on Board postings come straight from their datasets and never touch the `companies`
table.

**What V2 should do:**

- A "not interested" action on each card, working across every source.
- A single `blocked_companies` table, read by every filter node — `Filter YC` and `Filter GOB`
  included. This replaces both the manual `UPDATE companies SET status = 'inactive'` and the
  hardcoded `STAFFING` regex.
- A company panel in the app: list all companies, activate/deactivate, see how many postings
  each one contributed.
- Search rules editable from the UI — minimum salary, maximum company size, which titles count
  as engineering. These currently live hardcoded in four Code nodes and have to be kept in sync
  by hand. They have already drifted once: `Filter ATS` kept an older `classify` for weeks after
  the other nodes were fixed.

The goal is that n8n stops being something you open.

## 3. AI: from list, to shortlist, to application

This is the section that changes what the product is. Today Hunter answers "what is out there".
With this it answers "which of these are for you, and here is the CV to send".

Everything here runs **in the app, on demand** — never inside the n8n schedule. Scoring 639
postings twice a day would cost real money; scoring the ones actually being looked at costs
cents.

### 3.1 Prerequisite: job descriptions on demand

`jobs.description` is almost always empty. Ashby and Lever return the full text in the board
response; Greenhouse and Workday only return it when a single posting is requested by id.

Without the description there is nothing to match against — the comparison would be CV against
job title.

**Fetch it lazily.** When a posting is opened in Hunter and has no description, an endpoint
retrieves and stores it. That is roughly twenty fetches a week instead of 639 twice a day.

This is the blocker for everything else in this section.

### 3.2 Prerequisite: the CV as data

`main.typ` is the presentation layer. Alongside it, the CV needs to exist as a structured
profile: years of experience, team sizes led, stack, domains, achievements with numbers,
seniority. Generated **once per CV version** and stored.

This is not an implementation detail, it is what makes the rest cheap and consistent:

- Each call sends ~500 tokens of profile instead of ~3.000 tokens of CV.
- Scoring stays comparable across postings, instead of varying with how the model happened to
  read the document that time.

A `cv_versions` table holds the Typst source, the parsed profile and a timestamp. Every derived
artifact references the version it came from.

### 3.3 Match score

New columns on `jobs`:

| Column | Contents |
|---|---|
| `match_score` | 0–100 |
| `match_strengths` | the three points where the fit is strongest |
| `match_gaps` | what the posting asks for that the CV does not show |
| `match_reasoning` | two lines explaining the score |
| `match_cv_version` | which CV version produced it |

Cached on `(job_id, cv_version)` — recalculated only when the CV changes. Hunter then sorts by
score instead of by priority, which is what turns a list of 639 into "these eight are for you".

The score is a **sort order, not a filter**. Nothing gets hidden because a model scored it low —
the same principle as role priority in V1.

### 3.4 Tailored CV per posting

The flagship feature, and the reason keeping the CV in Typst matters: it is code, so it can be
diffed, versioned and edited precisely by a model. A PDF cannot.

The flow:

1. From a posting in Hunter, with the match already computed, press **"Generate CV for this
   posting"**.
2. The model receives `main.typ`, the structured profile and the job description.
3. It returns **a diff against the Typst source**, not a new document: summary reordered,
   relevant bullets promoted, Core Skills resequenced, the posting's vocabulary adopted where it
   is honest to do so.
4. The variant is saved against that posting, compiled to PDF, and kept — so there is a record
   of exactly which CV went to which company.

**Two hard rules for the prompt**, which matter more than they look:

- **Never invent experience.** Only reorder, rewrite and emphasise what is already there.
- **Never change dates, employers or job titles.**

If the model is allowed to add material, sooner or later a CV goes out with a fabrication in it
that nobody noticed. Returning a diff rather than a finished file is the other half of that
safeguard: the change is reviewable before it is sent.

### 3.5 What "ATS optimisation" actually means

Worth being blunt, because this space is mostly marketing. Greenhouse, Ashby and Lever do not
reject a candidate on a hidden score. They parse the document into fields and a human reads the
result. The "ATS score" sold by online tools does not correspond to anything those systems
compute.

What genuinely affects the outcome:

- The PDF must be extractable text, not an image. Typst already produces clean text.
- Section headings should be conventional (Experience, Education, Skills) so the parser maps
  them.
- No text in headers, footers or unusual column layouts, which is where parsers lose content.
- Keyword presence matters, but because **recruiters search by keyword**, not because a filter
  runs automatically.

**So the feature worth building is not a score.** It is **"see what the ATS sees"**: run the
generated PDF through a text extractor and show the plain result. Anything that looks wrong
there will look wrong in the ATS. Zero AI cost.

The one part that does need a model is **requirement coverage**: against this specific
description, which requirements and terms the CV does not mention. That is concrete and
actionable — and it is already what the generation step in 3.4 consumes.

### 3.6 Recruiter outreach draft

Many of these roles are won through a LinkedIn message, not the application form. A four-line
draft per posting, with the specific angle for why the fit is there. It reuses the context
already assembled for the match, so it is nearly free.

### 3.7 Company brief

Funding round, investors, what the company actually builds, who the hiring manager is likely to
be. Generated **once per company** and reused across all of its postings. Useful for
prioritising, and again before an interview.

Storage already exists: `companies.sector` and `companies.stage` are never written by n8n.

### 3.8 Cost model

| Step | Model | Frequency |
|---|---|---|
| Parse CV into profile | good | once per CV version |
| Match score | small | once per posting per CV version, cached |
| Requirement coverage | small | folded into generation |
| Tailored CV, outreach draft | good | only on button press — 10–20 a month |
| Company brief | small | once per company |

The expensive mistake would be scoring inside the n8n schedule. As long as the AI lives in the
app and runs on demand, the spend is negligible.

## 4. The platform beyond Hunter

Hunter finds postings, Tracker follows the processes, CV produces the document. A few things sit
across all three.

**Follow-up reminders.** n8n is already running. A scheduled task that reads Tracker and flags
"applied to X eleven days ago, no response" needs no AI at all.

**Analytics on your own search.** This is the thing no external tool can provide, because it
needs your data: response rate by source, by salary band, by match score, and by whether the CV
was generic or tailored. After three months it answers whether the tailored CV actually helps or
is a placebo, and which sources to switch off.

It is also the honest test of section 3. Without it, the AI features are a matter of faith.

**Learning loop.** When a posting is marked rejected or discarded, capture why in one line. That
history goes into the scoring prompt, so over time the score reflects your criteria rather than
a generic notion of fit.

**Interview prep.** The company brief from 3.7 plus the match gaps from 3.3 are most of an
interview prep sheet already.

## 5. Data quality

**Currencies.** Salaries are compared as if every number were USD, so a posting listed as
`£80 - £150 GBP` passes the USD 60k floor incorrectly. Fix: detect the symbol/ISO code, store
`salary_currency` properly, and convert to USD before comparing.

Get on Board makes this sharper: its salaries are **monthly** USD, converted to annual in
`Filter GOB`. The same trap appears with any source that publishes monthly figures, which is
most of LATAM.

**Company HQ.** Filled from YC when available, otherwise inferred from the most frequent on-site
location across a company's postings. It can be empty or approximate. LinkedIn would give the
real value.

**Legal name vs. trading name.** Some boards are registered under a holding company: Amplemarket
publishes under `andotechnologies`, so its postings carry the legal name. Cosmetic, but it makes
searching by company name fail.

**People in Argentina per company.** The strongest signal that a company really hires here, and
the one piece of V1 that was never built. LinkedIn only exposes it to logged-in sessions, so the
plan was a Playwright script running on the local machine with the user's own session, ~25
companies per run, writing back to `companies.employees_ar` through a webhook. Worth doing, but
it is the most fragile part of the system and carries some account risk, which is why it was
left last.

**Workday pagination and false closures.** `Fetch Workday` pages three deep per search term. At
companies with very large boards, an open posting can fall outside that window, stop being seen,
and be marked closed by mistake. If that starts happening, raise `MAX_PAGES`.

## 6. Operations

**Move n8n off the laptop.** While it runs on a local machine, a scheduled run is missed
whenever the machine is asleep — which is why workflow 3 fires twice a day as a workaround. A
small VPS removes the problem. Keep `N8N_ENCRYPTION_KEY` from the current install, or the stored
credentials cannot be decrypted after the move.

**Failure alerts.** Today a broken workflow is noticed only because no new postings show up. An
Error Trigger sending a message (email, Telegram) would close that gap.

**Upstream dataset monitoring.** Both datasets are community projects rebuilt daily. If one
stalls, the pipeline keeps running on stale data with no warning. A check on their
last-updated timestamps would catch it.

**Filter drift.** The shared rules block is duplicated across `Filter ATS`, `Filter Workday`,
`Filter YC` and `Filter GOB`, and they have already fallen out of sync once. Either move the
rules to the database (section 2) or extract them into a sub-workflow that all four call.

---

## 7. Multi-user

`jobs.user_id` exists today even though postings are objectively global, which keeps the
single-user product simple. If the app ever serves more than one person, the same posting would
be duplicated per user.

The migration: a global `jobs` table plus a `user_jobs` join carrying `status`, `notes` and
`applied_at`. The column-ownership split documented in `docs/architecture.md` already draws the
line where the cut would be made.

Note that the AI features in section 3 are per-user by nature — match score, tailored CV,
learning loop — so they belong on the join table, not on `jobs`. Worth keeping in mind while
building them, even with a single user.

---

## Suggested order

1. **Job descriptions on demand** — blocks everything in section 3.
2. **CV as structured data** — done once, enables the rest.
3. **Match score, and sort Hunter by it** — the biggest jump in day-to-day usefulness per unit
   of effort.
4. **Tailored CV with a reviewable diff** — the flagship feature, but it needs the three above.
5. **"See what the ATS sees"** — cheap, useful, no AI.
6. **Blacklist and rules in the database** — stops the need to touch SQL or n8n, and fixes the
   filter drift.
7. **Follow-up reminders** — small, no AI, keeps applications from going cold.
8. **Analytics** — starts paying off at thirty or forty applications, and it is what tells you
   whether the rest of this list was worth building.
9. **Currencies, VPS, alerts** — before treating this as something you rely on.
10. **LinkedIn headcount** — highest value per posting, most fragile; do it once everything else
    is stable.
